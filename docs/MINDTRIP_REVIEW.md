# JacRoam：Mindtrip 实机体验与改进建议

观察日期：2026-11-16。通过 Chrome 访问用户截图对应的 [Osaka and Kyoto 行程](https://mindtrip.ai/trip/t-JrlQUglt)，实际打开了行程首页、Itinerary、Day 2 的 Day map、伏见稻荷地点详情与 Trip preferences。没有修改这份行程、发送聊天或提交预订。

## 本次已实现

- 应用名称、浏览器标题、AI 自称、助手消息署名、项目说明与地图服务请求标识统一为 **JacRoam**。
- 普通行程第一次打开地图时，会分批查找缺失地点坐标。入口适用于手动创建的行程和用户接受后保存的 AI 行程，不调用 demo 数据接口。
- 唯一匹配保存到行程数据库；多候选要求用户确认；失败或无结果保留状态，可主动重试。刷新不会不断重复同一个失败查询。
- 使用每个地点所属的城市作为查询上下文。离线城市小字典之外的城市，可以通过地理查询或已定位地点建立地图中心。
- 用户确认的实际飞行轨迹保存到数据库。另一浏览器访问同一服务、同一行程可以恢复；修改航班名称、日期或地点会让旧轨迹失效。地图数据保存不改动行程安排或预算。
- 按用户确认，本次范围是通用代码与本地验证。没有公网部署、账号体系或不同本地安装之间的同步。

## 实际观察与对应改进

| JacRoam 当前能力 | Mindtrip 页面实际呈现 | JacRoam 应如何改进 |
| --- | --- | --- |
| 对话生成行程、审核保存 | Trip 首页显示行程摘要、下一步建议、该 Trip 的 Chats，以及新聊天输入框 | 让一个行程拥有多个有标题的对话。新对话继续引用同一份已保存行程，不把聊天记录当成唯一的旅行状态 |
| 地图与城市／日期／类别筛选 | Google 底图；带类别图标与加入状态的地点标记；总览地图和每天独立的 Day map | 共用城市、日期、选中地点状态；点击一天同时更新列表与地图范围；密集标记聚合，点击展开 |
| 地点详情和可选照片 | 可展开的侧边详情面板；照片与署名、评分来源、介绍、评论、地址、导航、保存和 Added 状态 | 统一地点实体，保存 provider ID、规范地址、坐标、照片来源和核验时间；地图和列表打开同一个详情抽屉 |
| 普通地点与行程项目 | Ideas 与 Itinerary 分区，地点可 Save，也可加入行程；同一地点有独立详情 | 明确区分“收藏”“候选”“已安排”“已预订”。不要让一个蓝勾同时代表已加入、已完成、已核实 |
| 多城市路线与行程时间 | 按 Day 分组，显示活动起止时间；酒店有入住、离店、连住表达；相邻地点间有距离与 Directions | 把住宿表达为日期区间；将交通作为两个活动之间的段落；显示本地时区、预计交通时间和缓冲，路由未核实时明确标注 |
| 预算、预订、偏好分别有页面 | 行程名下用城市、天数、Who、Budget 胶囊摘要；Ideas、Itinerary、Bookings、Media、Trip preferences、Calendar 使用清晰入口 | 把常用信息放在行程页顶部；高级参数放进详情；让“查看安排”“找灵感”“处理变化”有明确主入口 |
| 延误影响与 Plan B 审核 | 本次浏览未验证 Mindtrip 的延误传播、约束验证或替代方案事务保存能力 | 保留 JacRoam 的依赖分析和验证能力；将其呈现为清楚的影响清单、前后对比、额外支出和一键确认，而不是分散在多个技术功能页 |
| 实际飞行轨迹 | 本次看到真实底图与地点导航，没有验证 Mindtrip 的实际 ADS-B 飞行轨迹能力 | 轨迹作为航班详情的可展开能力。主流程输入航班号与日期，显示来源、机号、时间与覆盖缺口；不要把地理连线称为实际飞行轨迹 |

地图供应商 Google 可从页面署名直接确认。页面背后的模型、数据库、地理解析和调度算法没有公开到可核实的程度；上表关于 JacRoam 数据实体与实现方法的内容是设计建议，不是对 Mindtrip 内部架构的断言。

## 建议实施顺序

### P0：统一行程工作区

桌面采用导航栏 + 主内容 + 地图两栏工作区，地点详情使用可关闭、可展开的抽屉。对话可按需展开，避免同时出现三个争夺宽度的侧栏。地图下方现在还完整重复了时间线与 Places 面板，应改成清晰的视图切换。

同一个选中日期、城市和地点驱动地图、列表及详情。切到下一天时自动适配该天地点；点列表卡片时地图定位并突出对应标记；关闭详情后保持原来的筛选和滚动位置。手机采用地图／列表切换与底部详情面板。

### P1：地点与状态更可信

把地点照片、地址、营业信息、信息来源及更新时间放在相同位置；加载、无结果、多候选、离线和过期信息各有可理解的状态。详细地址和外部导航能直接使用。照片、评论和评分仅显示真实来源，不用模型生成的值填满 UI。

将地点收藏、候选与正式行程分离。新增地点先进入候选，选择日期和时间后再加入行程。更换地点时同步处理坐标、交通时间、预算与相关约束，保留用户确认步骤。

### P1：把 JacRoam 的优势放到用户面前

出现延误时，在同一工作区显示“航班晚到 → 哪些安排受影响 → 推荐调整 → 哪些预约保持”。展示所依据的时间、政策和价格来源；确认前对比额外支出、损失、冲突和待确认项；保存后保留修订记录。

### P2：减少旅行准备成本

支持导入预订邮件／收据、提取航班与酒店信息，供用户确认后写入 Bookings；随后再做共享协作、账号隔离与跨设备同步。此阶段需要单独设计权限和部署，不应把共享原型数据库直接作为公开多用户服务。

## 视觉原则

- 延续截图中的浅色背景、明确留白、统一线性图标、圆角卡片和克制的强调色；替换目前含义不一致的 Unicode 类别符号。
- 保留 JacRoam 的品牌与主要操作色；地图颜色和状态色要有独立语义，红色主要用于需要处理的问题。
- 每个页面突出一个主操作。将 API key、ICAO 呼号、数据供应商等技术细节放在相关设置或高级详情，主流程使用旅行者熟悉的名称。
- 不复制没有功能支撑的控件。分享、邀请、预订、媒体等入口应在功能可用时出现，并说明真实执行结果。

本次已交付的是名称统一和地图通用化。上述工作区重组、地点资料扩充、收藏系统、预订导入与协作属于后续建议，尚未实现。

## 本地验证

- 49 项后端测试通过，覆盖普通新行程、分批定位、候选确认状态、查询失败、并发编辑、轨迹保存及失效；4 个 Jac 编译入口通过。
- Chrome 通过正常表单创建 Reykjavik discovery，仅输入地点名称。Hallgrímskirkja 唯一匹配后自动保存；Harpa 返回多个候选，选择后保存。两处地点在另一个浏览器中恢复，并能进入 Reykjavik 城市地图。
- 真实服务返回 ANA37／JA830A 在 2026-11-15 的 ADS-B 记录；保存到行程后刷新恢复。实际记录依赖供应商覆盖，网页搜索结果不会被当作坐标轨迹。
- 窄屏验证没有页面横向溢出。没有测试真实手机硬件或公网访问；本次也没有使用 OpenAI key 运行新的付费行程生成，AI 草稿接受后写入同一 items 数据表的路径已检查。
